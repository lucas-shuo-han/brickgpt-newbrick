| | 原 8 种 | +1x3 | +2x3 | +1x10 | +1x12 |

## 2. Gurobi bug：影响 6.8% 的数据集结构（好消息，可以写）
从测试集随机抽 500 个结构（数据集本来就是挑过"稳定"的），同一个结构分别用原代码和修正后的代码打分：

| | 原代码 | 修正后 |
|---|---|---|
| 判为不稳定 | 44 / 500（8.8%） | 10 / 500（2.0%） |

- **34 个（6.8%）是被 bug 误判的**：修正后的分数几乎都是 0.000–0.013，只有 1 个是 0.114，都远小于 1。
- 也就是说，原代码判"不稳定"的结构里，**大约 3/4 其实是稳定的**。
- 之前 33 个结构的小样本估计是 15%（5/33）；500 个的估计更可靠，是 6.8%。
- 修正后仍有 10 个 ≥ 1。它们是真的不稳，还是还有别的数值问题：**未查**。
- 两种打分速度一样（中位数约 18 秒/结构）。
- 文件：`bug_out/bug_impact.jsonl`、`bug_out/bug_impact_summary.json`。

## 3. Bug 会不会改变 BrickGPT 自己生成的结果？会，12 个里有 2 个变了
同样的描述、同样的随机种子，开启回滚（rollback），本地 CPU 跑两遍：一遍用原代码检查稳定性，一遍用修正后的。12 个物体（第 0–11 号）全部跑完。

| 物体 | 两遍一样？ | 回滚次数（原 / 修正） | 砖数（原 / 修正） | 最终结构的修正后分数（原 / 修正） |
|---|---|---|---|---|
| 0 | **不一样** | 2 / 11 | 79 / 335 | 0.164 / 0.046 |
| 8 | **不一样** | 1 / 0 | 37 / 89 | 0.019 / 0.000（原代码给这个 89 块的打了 1.0） |
| 其余 10 个 | 完全一样 | 相同 | 相同 | 相同 |

- **第 8 号**：修正版直接生成了一个 89 块砖、完全稳定的结构；原代码把它误判成不稳定，触发回滚，最后变成一个 37 块砖的不同结构。**bug 让 BrickGPT 白白扔掉了一个好结构。**
- **第 0 号**：两遍在中途分叉。修正版最后做出一个更大（335 块）、修正后分数更低（0.046 vs 0.164）的结构，但回滚了 11 次，在 CPU 上用了 5.9 小时（原代码 2.1 小时）。所以**修正 bug 不一定更快**。
- 两遍的最终结构用修正后的代码打分，都没有不稳定的（0/12 对 0/12）。
- 回滚次数合计：原代码 19 次，修正版 27 次（几乎全来自第 0 号）。
- 时间不能直接比：两组同时在同一台电脑上跑，还和其他实验抢 CPU。完全相同的物体也差了好几倍时间。
- 结论：12 个里 2 个（17%）的生成结果被 bug 改变了。样本太小，比例不可靠；要可靠的数字，需要在 GPU 上跑 50–100 个。
- 文件：`bug_out/gen_compare.json`、`bug_out/gen_on_*.jsonl`。
