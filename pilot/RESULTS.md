# 1x3 积木 pilot 实验结果（2026-11-04，本地 CPU）

**问题：** BrickGPT 原本没有 1x3 积木。只靠 context（prompt / 示例），模型会用新积木吗？

## 设置
- 模型：BrickGPT 官方 LoRA + Llama-3.2-1B-Instruct（底座用 unsloth 的公开镜像，权重相同）。权重冻结，只改 prompt。
- 1x3（LDraw part 3622）在运行时加入积木库，因此不会被当成非法积木拒绝。
- 1x3 数据：把 StableText2Brick 里相邻、共线的 1x1+1x2 合并成 1x3，不需要新标注。test 集共 2851 个结构，平均每个 112 块积木、约 4.6 处可以合并。
- Prompt 条件：原始 prompt；允许列表加入 1x3；再加文字描述；few-shot k=1；few-shot k=3（示例为合并后的真实结构）。

## 探针 A：空 g 格的墙（只有 g=3 时 1x3 正好放满）
在能放进去的积木里，模型选 1x3 的概率：

| 条件 | gap=3 |
|---|---|
| 原始 prompt | 0.1% |
| 列表加 1x3 | 0.1% |
| 加描述 | 0.2% |
| few-shot k=1 | 0.1% |
| few-shot k=3 | 0.1% |
| **LoRA（150 例，1 epoch）** | **8.8–11.1%** |

所有条件下，1x3 都不是概率最高的选择（top-1 为 1x3 的比例是 0%）。

## 探针 B：真实结构里可以放 1x3 的位置（40 个结构）
指标：P(1x3) / (P(1x3) + P(原来那块积木))。

| 条件 | 平均 | 前缀里已有 1x3 | 前缀里没有 1x3 |
|---|---|---|---|
| 原始 prompt | 8.9% | 11.5% | 0.0% |
| 列表加 1x3 | 5.1% | 6.8% | 0.0% |
| 加描述 | 5.2% | 8.0% | 0.0% |
| few-shot k=1 | 12.7% | 22.1% | 0.0% |
| few-shot k=3 | 8.2% | 12.1% | 0.1% |
| LoRA + 原始 prompt | 27.7% | 33.8% | 6.7% |
| LoRA + 列表加 1x3 | 29.2% | 32.7% | 18.6% |

## 结论
1. **只靠指令或示例，基本无效。** 告诉模型"有 1x3"，它也不会用。这和 Wei et al. 2023 一致：小模型、重度微调过的模型很难被 in-context 信息覆盖掉先验。
2. **它会"复制"自己前面的输出。** 如果前缀里已经有 1x3，P(1x3) 会从 0 涨到 7–22%。模型对自己输出里出现过的模式有反应，但不会执行规则。
3. **in weights 学得会，但很慢。** CPU 上训一个极小的 LoRA（42 分钟），P(1x3) 就涨了大约 100 倍。不过它在 gap=4、5 时也同样常用 1x3，说明学到的是"1x3 存在"，还没学到"该在哪里用"。
4. **对项目的意义：** 方向是可行的。故事可以改成：in-context 失败、in-weights 成功，并研究中间的方法能否把这个差距补上，例如训练模型"读积木库"（条件 E）、多示例、或把新积木放进前缀。

## 探针 C：必须用 1x3 的任务（悬挑）
Prompt 里写明目标："在 z=1 层正好盖住这几格，不能有悬空积木，块数越少越好"。前缀里只放支撑用的 1x1。打分的是第一块顶层积木 `1xw (x0,y0,1)`，w=1..4。每个条件 12 个样本。
- need_end：长度 3，只有一端有支撑 → 只有 1x3 可行
- need_mid：长度 3，只有中间有支撑 → 只有 1x3 可行
- ctrl_full：长度 3，下面全有支撑 → 用不用 1x3 都行
- ctrl_end2 / ctrl_end4：长度 2 / 4，一端有支撑 → 只有 1x2 / 1x4 可行（用旧积木检查模型懂不懂任务）

| 条件 | P(1x3) need_end | need_mid | ctrl_full | 首选正确 need_end | ctrl_end2 (1x2) | ctrl_end4 (1x4) |
|---|---|---|---|---|---|---|
| base 原始 prompt | 0.0% | 0.1% | 0.1% | 0% | 58% | 8% |
| base 列表+描述 | 0.1% | 0.5% | 0.1% | 0% | 58% | 0% |
| base few-shot（4 个已解示例） | 1.3% | 1.5% | 0.1% | 0% | 67% | 50% |
| LoRA150 原始 prompt | 9.8% | 15.3% | 8.1% | 0% | 50% | 0% |
| LoRA150 列表+描述 | 18.8% | 24.3% | 13.0% | 0% | 67% | 0% |

| LoRA250 原始 prompt | 8.7% | 12.3% | 11.3% | 0% | 50% | 8% |
| LoRA250 列表+描述 | 16.5% | 19.9% | 16.8% | 0% | 67% | 8% |

LoRA250：250 个例子，1 epoch，CPU 约 77 分钟，val loss 0.27 → 0.189。和 150 例时（0.188）一样，已经不再下降。

**解读：**
- 数据从 150 例加到 250 例，没有带来提升。LoRA250 在"必须用"和"不必用"时用 1x3 的概率完全一样（约 17%）。用 caption→结构的数据训，模型只学到"1x3 是一种常见积木"，学不到"什么时候必须用"，因为训练数据里根本没有"必须"这个信号。
- 即使只用旧积木（ctrl_end4，1x4 正好解），base 模型首选 1x4 的比例也只有 0–8%。它**根本不读 prompt 里的任务描述**。BrickGPT 只学过"根据 caption 搭物体"，不会执行指令。
- few-shot 有一点效果：1x4 首选率升到 50%，P(1x3) 从 0 升到 1.3%。
- LoRA 让 1x3 的概率普遍上升，但"需要"和"不需要"时差不多（need 19–24% vs ctrl_full 13%）。它对"是否必须"只有一点点敏感。
- **对项目的含义：** "必须用新积木"的评估，前提是模型能看懂目标。可以做的方式：
  - (a) 训练时就用这种"带目标的任务格式"，即 LoRA/条件 E 学"读目标 + 读积木库"；
  - (b) 不在 prompt 里写目标，改用物理检查当裁判：生成后检查有没有悬空、块数多少；
  - (c) 换一个本来就会听指令的底座模型（比如 Qwen 0.8B–9B），把 BrickGPT 当作 in-weights 基线。

## 生成实验：让模型从头搭整个物体（1x3 已在积木库里，prompt = 列表+描述）
"本可合并" = 生成结果中相邻、共线、可以换成 1x3 的 1x1+1x2 对数。

| 模型 | 物体数 | 用了 1x3 | 本可合并 |
|---|---|---|---|
| base | 2 | 0 | 17 |
| LoRA250 | 3 | 1 | 13 |

在真正生成时，两个模型几乎都不用 1x3。样本很少，只能当作定性参考。每个物体在 CPU 上要 2–6 分钟。

## 总结（给老师 / 队友）
1. **只靠 context（指令、描述、few-shot），模型不用新积木。** 在必须用 1x3 的任务上，它连"按任务描述放积木"都做不到，换成旧积木也一样。
2. **in weights（小 LoRA）能把 1x3 的使用率提高约 100 倍，但学不到"什么时候必须用"**，而且 150→250 例没有带来提升。
3. 下一步建议：
   - 构造**带"必须"信号的训练/评估任务**：悬挑、桥、块数预算，用物理检查当裁判。
   - 测试"读积木库"的 LoRA（条件 E）。
   - 或者换一个**会听指令的底座模型**（Qwen），检验是不是 BrickGPT 太"专"导致的。

## 局限
- 只用 CPU，样本量小：探针 A 每个条件 40 条，探针 B 40 个结构。没有 error bar，也没有多个 seed。
- 探针 B 在不同条件下随机抽到的合并位置不完全一样（随机数状态不同）；LoRA 的对比用的是同样的位置。
- 稳定性检查用的是 connectivity，没有用 Gurobi。
- 生成实验见 `results_gen*.json`。
